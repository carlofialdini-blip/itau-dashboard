## 1. Project Overview

- **Name:** Portfolio Intelligence Dashboard (internal working name; header reads "Portfolio Intelligence / Market Monitor")
- **Owner:** Carlo Fialdini (vittorio.fialdini@gmail.com), works at Itaú
- **Purpose:** Aggregate news, market data, and economic indicators for a tracked portfolio of Brazilian/global companies, plus dedicated Brazil, China, and Credit-market views. Built for internal team distribution — not a live web app.
- **Distribution model:** Generated **twice a day** into a single static `dashboard.html` file, then uploaded to SharePoint / sent directly to teammates. Recipients just open the file in a browser — no server, no install, no network calls at view time. This shaped almost every architectural decision below.
- **Tech stack:** Python 3 (stdlib + a handful of libs, see §5), Jinja2 templating, vanilla JS, Plotly.js (via CDN in the template). No frontend build step, no npm/Node runtime dependency for the app itself, no database.
- **Package manager:** pip, `requirements.txt` at repo root.
- **Repo:** `git@github.com:carlofialdini-blip/itau-dashboard.git` (GitHub account `carlofialdini-blip`, distinct from `carlofialdini` — SSH key is tied to the `-blip` account).

## 2. Architecture

### Data flow (what `update_dashboard.py` runs, in order)
1. **Scrapers** (`scrapers/*.py`) — query Google News RSS per sector/company, score relevance, merge with existing cache → write `data/*_cache.json`. **Freshness policy differs by source**: `brazil_scraper.py` is strict same-day-only (Brasília calendar date), with per-keyword querying (not one OR-mega-query — see §4) and score-based backfill to a 30-article-per-sector floor; `scraper.py`/`china_scraper.py`/`credit_scraper.py` keep a 7-day day-balanced window (today/yesterday/older fallback buckets); `scraper.py`/`credit_scraper.py` also query per-keyword now, same fix as `brazil_scraper.py`'s (see §4).
2. **Event generators** (`events/*.py`) — build forward-looking event calendars (mix of live APIs and hardcoded annual schedules) → write `data/*_events.json`.
3. **`scrapers/fuel_scraper.py`** — downloads ANP's `liquidos.zip` open-data file, parses ~1M rows of company-level fuel-distribution sales, aggregates into the Energy sub-page's `{E,P,R,M,T,G,K}` shape → writes `data/fuel_data_cache.json`. Not news or an events calendar (hence not grouped under 1/2 above), but wired into `update_dashboard.py`'s `STEPS` the same fault-isolated way — its own subprocess, own timeout, and a failure here just means the Energy page keeps its last-cached snapshot rather than blocking the rebuild.
4. **`core/generate_dashboard.py`** — reads all cache files + `portfolio.xlsx`, fetches *live* chart data (BCB OLINDA API for Brazil/Credit macro series, chinadata.live API for China datasets, yfinance + BCB + ANBIMA for the Cockpit market overview), **merges all 4 news sources and all 3 event sources into two unified feeds** (`load_unified_news()`, `load_unified_events()` — see Architecture below), renders `templates/dashboard_template.html` via Jinja2 → `dashboard.html`. Every chart's data is embedded inline as JSON in a `<script>` block — the file has zero `fetch()`/XHR calls, so it opens correctly via `file://` with no server.
5. **`update_dashboard.py`** orchestrates 1–4 via `subprocess`, **continues past individual step failures** (a network hiccup in one scraper doesn't block the rebuild — that source just keeps its last-cached data), 600s timeout per step.
6. **`setup.py`** = `pip install -r requirements.txt` then delegates to `update_dashboard.py`. Run once per machine (Carlo's Mac, the work Windows PC) — never sent to teammates.

### Pages in `dashboard.html`
As of the July 2026 reorganization, the dashboard is organized by **content type**, not by source — one News page instead of four separate news feeds, one Economic Data page instead of three chart grids, one Calendar instead of three event lists. Scrapers/generators are still one-per-source internally (see Data flow above); the merging into unified pages happens once, in `core/generate_dashboard.py`, not in the underlying pipeline.

- **Cockpit** — Market Overview only (Equities/Interest Rates/Exchange Rates/Commodities cards). No tabs — this is the one page that stayed single-purpose, since "market data" doesn't fit the news/data/calendar shape the other three sources share. Commodities: Brent Crude, Iron Ore, Natural Gas, Diesel, Gasoline, Gold, Silver, Copper, Aluminum, Nickel, Jet Fuel (11 total — the old Suzano/Klabin pulp-price proxies were removed, see §4). Every card on every group — not just Commodities — carries a small "ⓘ" icon (hover tooltip, `ICON_INFO`) showing exactly which data provider it came from (`item.source` in `core/generate_dashboard.py`'s `_ck_make()`).
- **News** — unified feed: Portfolio + Brazil + China + Credit articles, one list sorted strictly by recency (never resorted by importance). Filters: search box, **Country** (Brazil/China — Portfolio and Credit are both tagged Brazil since portfolio companies are B3-listed and credit news is the Brazilian credit market), **Sector** (one flat merged list across all sources — Credit's categories like "Recuperação Judicial" sit in the same dropdown as Brazil's/China's sector names), **Company** (populated only from the ~10 portfolio-tracked companies — the only source with company-level data), **Source** (multi-select checkbox list, e.g. select CNN Brasil + Valor Econômico simultaneously — `news_sources` is every distinct `a.source` value across the whole unified feed, ~174 with China's feed included since that one isn't domain-whitelisted; the checkbox list has its own client-side search-within-filter to stay usable at that count, separate from the main headline search box). **News Clipping**: "Generate Clipping" button in the feed header → checkboxes appear on every card → either "Export Excel" (a real `.xlsx`, Date/Title/Link, Link as a genuine clickable hyperlink) or "Email Clipping" (a ready-to-forward `.eml` file, styled HTML with clickable article links) of just the selected articles — see §4 for the implementation.
- **Economic Data** — unified chart grid: all Brazil (BCB) + China (chinadata.live) + Credit (BCB) dataset cards in one flat grid, client-side-tagged by source and filterable via pills (All/Brazil/China/Credit). The merge happens in the browser (`buildEconCharts()` in the template's JS combines the three `*_DATASETS` JS globals with a source tag) — no Python-side data model change was needed for this page.
- **Calendar** — unified event list: Brazil + China events, with Portfolio's (Cockpit's) earnings/COPOM events folded into the Brazil bucket. Filter: Country pills (All/Brazil/China).
- **Other Datasets** — the China dataset catalog browser (`buildCatalog()`), relocated to its own top-level page. Contents unchanged, stays China-only.

### Shared chart UI (standardized across every chart on every page)
- Every chart renders with Plotly's native modebar **off** (`displayModeBar:false`). Each card instead has small icon buttons in its header: **PNG**, **CSV**, **Expand**.
- **Expand** opens one shared modal (`#chartModal` / `.chart-modal*` CSS, `chartExpand()` in the template's JS) used by every chart — not a per-page component.
- Cockpit's FX cards (Exchange Rates group) are stat-only by design — big number + CSV download, no chart, no expand.
- The Economic Data page's chart grid is **one flat grid** for all 3 sources combined (no per-sector or per-source section breaks — see §4 for why); sector is shown via a colored left border + small tag per card, source via the pill filter, instead of hard row/page breaks.

## 3. Coding Standards

- **No comments explaining *what*** — code is expected to be self-descriptive via naming. Comments are reserved for non-obvious *why* (a workaround, a confirmed-bad external API, a subtle invariant).
- **Every scraper/event-generator file is self-contained**: each defines its own `HEADERS`, does its own `urllib3.disable_warnings()` + `sys.stdout.reconfigure()` at import time, computes `ROOT = Path(__file__).resolve().parent.parent`. This duplication is intentional — matches the project's "few files, each independently runnable" philosophy — except for genuinely cross-cutting concerns (HTTP retry logic in `core/net_utils.py`, importance-score bucketing in `core/scoring.py`, and the trusted-domain whitelist in `core/trusted_sources.py` — the last one specifically because 3 scrapers must apply the exact same rule, where duplication would risk drift).
- **All HTTP calls use `verify=False`** + `urllib3.disable_warnings(InsecureRequestWarning)` — required because the target corporate network (Itaú) intercepts HTTPS via a proxy with its own CA not in the `certifi` bundle. This is deliberate, not an oversight — do not "fix" it by re-adding cert verification without checking with Carlo first.
- **All HTTP calls go through `core.net_utils.get_with_retry()`** (2 attempts, backoff) rather than raw `requests.get()` — single-attempt calls were the root cause of a whole class of "0 articles fetched" bugs on flaky/corporate networks.
- **Windows compatibility:** every entry-point script calls `sys.stdout.reconfigure(encoding="utf-8", errors="replace")` **and the matching `sys.stderr.reconfigure(...)`** (added after a real crash — see §4/§8; stdout-only was a gap present since the original CP1252 fix) — Windows terminals default to CP1252 and choke on unicode (`→`, `—`, `…`, accented Portuguese characters) otherwise. Every `subprocess.run()` that captures a child's output also passes `encoding="utf-8", errors="replace"` (not just `encoding="utf-8"`) — a child process's own output isn't guaranteed to be valid UTF-8 even when this project's own code is careful, since third-party libraries can print warnings/errors through channels this project doesn't control.
- **Timezone discipline:** all article/display timestamps must be in **Brasília time** (`America/Sao_Paulo`), not raw UTC from feed sources. Centralized in `parse_date()` in `core/generate_dashboard.py` — convert there, not at each call site.
- **No premature abstraction:** the 4 scrapers and 3 event generators are near-duplicates of each other by design (different queries/sectors) rather than parameterized into one generic module — this was a deliberate choice matching "few files, easy to reason about one at a time" over DRY-at-all-costs.
- **Testing:** none currently. No test suite, no CI. Verification during this project's development has been manual: run the actual scraper/generator, inspect real output counts, syntax-check generated JS with `node --check`.

## 4. Important Decisions

Chronological, most-recent last. Only decisions with lasting architectural consequence — see git log for the full incremental history.

- **Windows CP1252 fix** — `sys.stdout.reconfigure()` + `encoding="utf-8"` everywhere. *Why:* Windows terminal crashed on unicode output. *Impact:* every script touches this pattern at import time. **Had a real gap**: `sys.stderr` was never reconfigured, only `sys.stdout` — caused an actual crash later in the project's life; see the later §4 entry ("Real crash on Carlo's Windows machine") for the fix.
- **`verify=False` on all requests** — bypasses the corporate SSL proxy's untrusted CA. *Why:* certifi-based fixes didn't work; this is the bank's network doing TLS interception, confirmed by Carlo. *Impact:* `certifi` dependency removed entirely.
- **Fully static output, no server** — removed the refresh button and (later) deleted `core/server.py` entirely. *Why:* the real usage pattern is generate-then-email/upload, not "browse a running server." *Impact:* `dashboard.html` has zero `fetch()` calls; all chart/news data is baked in as inline JSON at generation time.
- **News window: 1 day → 7 days, fixed in two places** — raising `MAX_NEWS_AGE_DAYS` in `generate_dashboard.py` alone wasn't enough; each scraper had its *own* `MAX_AGE_DAYS=1` and a `balance_by_day()` that only bucketed "today" vs "yesterday", silently discarding anything older even after the render-time gate was widened. *Fix:* raised `MAX_AGE_DAYS` to 7 in all 4 scrapers + added a third "older" fallback bucket to `balance_by_day()` in 5 places (4 scrapers + `generate_dashboard.py`). *Lesson:* when a filter exists in multiple layers, check all of them.
- **Retry logic (`core/net_utils.get_with_retry`)** — single-attempt `requests.get()` calls were silently zeroing out entire sectors/datasets on transient timeouts. *Impact:* wired into every fetch site; bumped `update_dashboard.py`'s per-script subprocess timeout from 180s → 600s to give retries headroom without false-timeout aborts.
- **PIX BHKP/NBSK pulp proxies → Suzano/Klabin stocks** — FOEX's real pulp index is paywalled; the FRED series originally used (WPU0912, US PPI) was a meaningless proxy. *Fix:* replaced with `SUZB3.SA` / `KLBN11.SA` (B3-listed, liquid, fetchable via yfinance) as pragmatic proxies. **Superseded**: Carlo asked to remove these entirely (see the Cockpit commodities-expansion entry below) — no replacement pulp/paper metric exists on the Cockpit anymore.
- **Brazil 10Y: 12511 (broken) → Selic (wrong metric) → ANBIMA ETTJ (correct, real)** — first swapped the broken BCB series 12511 for the Selic policy rate as an honest-but-different fallback; Carlo rejected that outright ("the values of the brazilian interest is not actually the future curve but actually the selic, which is not the same thing"). Found ANBIMA's free daily ETTJ download (`https://www.anbima.com.br/informacoes/est-termo/CZ-down.asp?Dt_Ref=DD/MM/YYYY`) — a real, market-derived nominal yield curve, verified against independent reporting (fetched 14.44% vs. investing.com's reported 14.43% for the same day). The free endpoint serves one date per request and only retains a few months of history, so `fetch_br10y()` accumulates a local `data/br_ettj_history.json` (same merge/append pattern as the news caches): a short backfill on first run, then just the newest day appended each subsequent run.
- **File reorg: root-level `update_dashboard.py` + `setup.py`, `core/server.py` deleted** — matches actual usage: Carlo runs `update_dashboard.py` twice daily, `setup.py` once per machine, teammates only ever receive `dashboard.html`. Also deleted `templates/china_template.html` (610 lines, unreferenced dead file from before China was folded into the unified template).
- **Cockpit Market Overview: above news → below news → own "Market Data" tab (first, default-active)** — iterated per direct user feedback; settled on tab pattern to match Brazil/China/Credit's existing tab-first convention.
- **Chart UI standardization** — disabled Plotly's native modebar everywhere (was overlapping tiny 100px Cockpit cards); unified every chart card to the same PNG/CSV/Expand icon-button row; generalized the Cockpit-only "mkt-modal" into one shared `.chart-modal` used by all 4 pages. Also fixed a bug where the modal plotted its chart *before* being shown (`display:none` at plot time → zero-width render) — fixed by show-then-wait-two-frames-then-plot.
- **Removed per-sector section headers in Economic Data grids** — each sector previously started its own CSS auto-fill grid row, leaving visible blank slots whenever a sector's dataset count didn't evenly fill a row. Flattened to one grid per page; sector now shown via a colored left border + small tag instead of a hard row break.
- **Itaú logo embedded as base64** — resized the original 3840×3840 source (`Itaú.jpeg`) down to 120×120 (`assets/itau_logo.png`) before embedding, to avoid bloating `dashboard.html` by ~500KB for a header icon.
- **Timestamps converted to Brasília time at the source** — Google News RSS publishes in UTC; `parse_date()` (the single choke point used by all 4 news feeds) now converts via `zoneinfo.ZoneInfo("America/Sao_Paulo")` immediately after parsing, so every downstream display (article time, header "Updated" stamp) is correct without touching each call site individually.
- **News importance badges (Low/Medium/High)** — every scraper already computed a `relevance_score()` to decide what clears `MIN_SCORE`, then discarded it (`del a["_score"]`). Kept it instead: `core/scoring.py` buckets it (`importance_bucket()`, thresholds High ≥8 / Medium ≥5 / Low below, same on every page), each scraper persists it as `importance_score` + `importance`, and the template shows it as a small badge on every news card. Sort order stays strictly recency-based per explicit instruction — importance is informational only, not a resort key. Thresholds were calibrated against real re-scraped data, not guessed: every bucket has meaningful representation on all 4 pages (see git log commit `1e731d9`).
- **Brazil scraper: 7-day window → strict same-day, generic keywords → technical per-sector keywords** — Carlo wanted Brazil news restricted to today only (Brasília calendar date) with analyst-level search terms per sector instead of generic ones, while still hitting a 30-article floor per sector. Discovered via direct testing that Google News RSS ranks results by *relevance*, not recency, and caps each query at ~100 entries — a single broad OR-query per sector returned **zero** today-dated articles out of 100 results, because the query's relevance budget got spent on one dominant sub-topic. Fixed by querying each keyword *separately* (one request per term, not one OR-mega-query), which surfaced real same-day results the mega-query missed entirely. Confirmed empirically that some niche sectors (Pulp & Paper, Energy) genuinely don't have 30 same-day articles most of the time — the 30-floor is best-effort with score-based backfill (same-day candidates only, never reaching into other days), not a guarantee, and that's a real content-volume ceiling, not a bug.
- **Major reorg: 4 source-pages → 5 content-type pages** — Cockpit/Brazil/China/Credit (each reimplementing its own News/Events/Charts tabs) replaced with Cockpit/News/Economic Data/Calendar/Other Datasets, each internally filterable instead of hard-partitioned by source. Planned via `EnterPlanMode` given the scope (touches nearly all of `templates/dashboard_template.html` and `core/generate_dashboard.py`'s render pipeline); full plan and the resolved ambiguities (country tagging, no separate "topic" axis, Calendar scope) are in the approved plan — see git log commit for this reorg for the plan file reference. Key resolutions: Sector is one flat merged list (Credit's categories sit alongside Brazil's/China's, no separate "topic" filter); Portfolio and Credit news/events are tagged `country="Brazil"` (Portfolio companies are all B3-listed, Credit news is the Brazilian credit market); Portfolio's COPOM entries are deduplicated against Brazil's (both generators independently schedule COPOM with byte-identical titles) rather than shown twice. Scrapers/event-generators themselves are untouched — the merge happens once, in two new functions in `core/generate_dashboard.py` (`load_unified_news()`, `load_unified_events()`), keeping each source independently refreshable.
- **Source whitelist: trust as a scoring bonus → trust as a hard domain filter** — Carlo flagged that "many articles are from unreliable sources" and supplied a ~130-outlet whitelist (Brazilian financial/business/trade press, wires, government agencies, sector trade publications). Previously each of the 3 Brazil-market scrapers (`scraper.py`, `brazil_scraper.py`, `credit_scraper.py`) had its own `TRUSTED_SOURCES` set of outlet *names*, used only as a `relevance_score()` bonus (+3/+2) — an untrusted-source article could still clear `MIN_SCORE` and get kept. Replaced with a hard pre-filter: `core/trusted_sources.py` (new shared module, `TRUSTED_DOMAINS` + `is_trusted(href)`) is checked against `entry.source.href` — Google News RSS's real publisher-domain field, confirmed via direct testing (`entry.source == {"href": "https://valor.globo.com", "title": "Valor Econômico"}`) to be more reliable than matching on `entry.source.title` (matching `entry.link`, a `news.google.com` redirect URL, isn't possible directly). Any article whose domain isn't in the whitelist is discarded before scoring; the now-redundant trust bonus was removed from all 3 `relevance_score()` functions. **Kept as one shared module** (unlike each scraper's usual self-contained-duplication convention, see §3) specifically because all 3 must apply the identical rule — one list avoids drift if Carlo asks to add/remove a domain later. Deliberately **not** applied to `china_scraper.py` — the whitelist is 100% Brazilian outlets; applying it there would zero out the China feed entirely. The existing caches held articles fetched under the old (bonus-only) rule, and `merge_articles`'s freshness-based carryover doesn't retroactively re-check trust on cached rows — so the change wouldn't have taken full effect until those aged out (up to 7 days for Portfolio/Credit, same-day for Brazil). Purged all 3 caches (`data/news_cache.json`, `data/brazil_news_cache.json`, `data/credit_news_cache.json` — gitignored, regenerable, not source data) and re-ran fresh rather than waiting. Confirmed post-purge outlet lists are 100% whitelist domains. Verified via live run: `brazil_scraper.py`'s 30-per-sector floor is no longer met at all post-purge (Economy 5, Energy 2, Mining & Steel 2, Pulp & Paper 0, Agriculture 9, Financial 14, Industry 10, Trade & FX 49 — 91 total) — this is the same "real content-volume ceiling, not a bug" situation as the earlier same-day-only change, now compounded by the domain restriction; flagged to Carlo rather than silently loosening `MIN_SCORE` or the date gate to compensate, which would defeat the point of the whitelist. Portfolio dropped to 70 total across 10 companies (Bradesco: 0). Credit dropped to 29 total across 7 sectors.
- **GDELT (`gdelt_scraper.py`), a second portfolio-news source — tried, never worked, removed.** Added originally to complement `scraper.py` after root-causing why Bradesco returned 0 whitelist-passing articles (the same OR-mega-query relevance-dilution problem `brazil_scraper.py` already had, plus its title-only phrase matching against Google's body-wide match). Batched to survive a ~150-company portfolio (`BATCH_SIZE`, lowered from 5 to 3 partway through on an explicit safety-over-speed call), incrementally checkpointed, ticker-aware for disambiguation. Despite that engineering, it **never once returned real article data across this project's history** — every attempt, including the first real validation run, hit GDELT's rate limit before completing, and the lockout's actual duration was never something this project could verify or control from outside. Carlo's call: eliminate it entirely rather than keep carrying a source that doesn't work as one more thing that can break. Removed: `scrapers/gdelt_scraper.py`, its `update_dashboard.py` step, its `load_unified_news()` merge branch in `core/generate_dashboard.py`, and the GDELT-only pieces of `core/trusted_sources.py` (`TRUSTED_DOMAINS_EN`, `DOMAIN_TO_OUTLET`, `outlet_name()` — all three had zero remaining callers once the scraper was gone; `is_trusted()` simplified back to a single-argument function since its `domains` override existed only for GDELT's dual domain-set need). News is back to 100% Google News RSS across all 4 remaining sources (Portfolio/Brazil/China/Credit). The real underlying coverage gap GDELT was meant to help with (Bradesco-style thin companies) is now addressed the other way — see the per-keyword-query fix below, which is the fix that was already proven for `brazil_scraper.py` and had been left "still outstanding" while GDELT was tried instead.
- **News page: added a Source filter, multi-select** — Carlo wanted to filter headlines by outlet (e.g. CNN Brasil + Valor Econômico at once), which the existing Country/Sector/Company filters (all single-select `<select>` dropdowns) couldn't do. `load_unified_news()` now also returns `news_sources` (every distinct `a.source` across the whole unified feed — **174** at the time this was built, since China's feed isn't domain-whitelisted the way Brazil/Credit/Portfolio are, so it pulls in a long tail of international outlets). At that count a plain checkbox list needed its own small search-within-filter to stay usable — a `#newsSourceSearch` input that just shows/hides `.src-item` labels client-side, entirely separate from the main headline search box (`#newsSearch`, which still searches `data-q`). Implemented as checkboxes (`.src-checkbox`), not a native `<select multiple>` — clicking a checkbox is a more discoverable "select several" affordance than ctrl/cmd-click on a listbox, and matches how a filter-sidebar checkbox list conventionally reads. The News filter JS's `apply()` gained one more AND-condition (`sources.size === 0 || sources.has(card.dataset.source)`) — empty selection means "no filter," consistent with every other filter dimension on this page defaulting to "All."
- **Cockpit: removed Suzano/Klabin pulp proxies, added 9 more commodities, added per-card source attribution to every metric on the page** — Carlo asked to drop the pulp & paper proxy cards (see the superseded entry above) and add Natural Gas, Diesel, Jet Fuel, Gasoline, Gold, Silver, Copper, Aluminum, Nickel, plus a visible source for every commodity *and* every other Cockpit metric (Equities/Interest Rates/Exchange Rates too). Verified every new ticker live before wiring anything in, the same standard as the Brazil-10Y/ANBIMA work — this surfaced two real data-availability problems that were resolved honestly rather than papered over:
  - **Jet Fuel has no clean free outright price.** Yahoo Finance's `JET=F` looked plausible until its full 6-month series was pulled: it oscillates between -0.48 and +0.50 with a mean near zero — a differential/crack-spread contract, not an outright price (an outright jet fuel price going *negative* would be a huge red flag on its own). Initially shipped as an honest "N/A" card — but Carlo flagged it (along with Nickel) as a "broken chart" in the next review pass, which is a fair read: a permanently-empty card looks like a bug even with a clear label. **Superseded**: removed from the Cockpit entirely rather than kept as a standing N/A — see the follow-up fixes entry below.
  - **Nickel has no Yahoo Finance ticker at all** (`LNI=F`, `NI=F`, `NID=F`, `NICKEL` all confirmed 404/delisted live).   - **`update_dashboard.py`'s fault-isolation guarantee was breakable by a slow step.** Its docstring promises "if one data source fails... it does not abort the whole refresh," but `subprocess.run(..., timeout=600)` had no `try/except` — a step exceeding the timeout raises `TimeoutExpired` straight out of the loop and kills the entire run, including the "Building dashboard" step. Genuinely reachable here: the BGS mining scraper already takes ~4 minutes on a *good* connection, and Comex pulls 50-100MB CSVs — behind an inspecting corporate proxy, 600s is not a comfortable margin. Now caught (along with `OSError`) and recorded as a normal failed step; timeout raised to a named `STEP_TIMEOUT = 900`. Verified by running a deliberately-hanging child process through both the old and new call shapes.
  - **`core/generate_dashboard.py`'s own live fetches had no cache at all** — the one place in the project without a safety net. Scrapers merge into `data/*_cache.json`, `load_*_data()` falls back to the last snapshot, `update_dashboard.py` continues past failures; but BCB/chinadata.live/yfinance/FRED were re-fetched from scratch every run and, on failure, simply rendered an empty chart. Added `_resilient()` + `data/live_fetch_cache.json` (gitignored like every other cache), wired through all 8 live fetches. Merging is **per item, not all-or-nothing**, because partial failure is the normal case here — Yahoo rate-limits so most tickers come back empty while FRED-sourced cards succeed in the same run. Verified with four scenarios: partial failure keeps fresh values and restores only the failed ones; total failure still renders real cached data; good cached data is never overwritten by an empty fetch; and the list-shaped company panels fall back per ticker.
  - **`dashboard.html` was written by truncating and streaming 12MB into the live file** — on a OneDrive-synced Windows folder (`OneDrive - Banco Itaú SA\...`) with the previous copy quite possibly still open in a browser, a lock or sync hiccup mid-write leaves a *corrupt* dashboard where a working one used to be. Now written to a temp file and `os.replace()`d atomically, with a `PermissionError` message that names the actual cause (close the browser, let OneDrive settle).
  - **`get_with_retry()` defaults made more patient** (timeout 15→30, retries 2→3) — the deployment target proxies and inspects every request, and has already produced real mid-transfer resets (WinError 10054 from CONAB/IBGE). Heavy callers still pass their own larger explicit timeouts.
  - **`_ck_yf()` guarded against yfinance API churn** — the bank machine runs yfinance 1.5.1, this dev machine 1.4.1. If a future version stops accepting `session=`, the call now falls back to a plain `yf.download()` (losing the TLS workaround but not turning every ticker into an exception) instead of failing outright. Verified with a stubbed `yfinance` that raises `TypeError` on `session=`.
  - **Audited and found clean**: no scraper passes a URL to `feedparser.parse()` (all four fetch via `get_with_retry()` first and pass `.content`), no `pandas.read_csv/read_excel` reads directly from a URL, and there is no raw `requests.get()`/`urlopen()` anywhere outside `net_utils.py` — so yfinance was genuinely the *only* library-level bypass of the `verify=False` workaround.
- **yfinance session backend: the `verify=False` fix was right, the HTTP backend was wrong — and it silently blanked every Yahoo-sourced card on the dashboard.** Carlo reported charts dead on the Cockpit and on Economic Data, having worked the day before. `get_yf_session()` (added the previous day, §4 above) handed yfinance a plain `requests.Session` to carry `verify=False`. yfinance's own `_http.new_session()` returns `curl_cffi.requests.Session(impersonate="chrome")` **because Yahoo fingerprints the TLS handshake (JA3/JA4) and HTTP/2 settings** — a plain `requests.Session` can't replicate that, and Yahoo answers it with HTTP 429 "Too Many Requests" on the very first call regardless of how little traffic was actually sent. So the fix traded the corporate-proxy failure for an instant rate-limit failure, and every caller's broad `except` turned that into empty data.
  - **The tell that made this unambiguous**: exactly 4 of 28 Cockpit metrics still worked — Brazil 10Y, iron ore, aluminum, nickel — which is precisely the set sourced from ANBIMA/FRED and never routed through yfinance. All 44 company cards on the Pulp & Paper / Mining / Agriculture panels were blank for the same reason. A single root cause, not a scattering of unrelated broken charts.
  - **Fix**: build the session on `curl_cffi` (`Session(impersonate="chrome", verify=False)`), keeping browser impersonation *and* the bank-proxy workaround at once, with a plain-`requests` fallback (browser UA + `verify=False`) only if `curl_cffi` isn't importable. `curl_cffi` is a hard dependency of yfinance (`curl_cffi>=0.15`) so it is always present in practice; it was added to `requirements.txt` explicitly anyway because `net_utils.py` now imports it directly — same reasoning as `urllib3`/`markupsafe` (§5).
  - **Verified live, and end-to-end in a real browser**: identical `yf.download("^GSPC")` returned **0 rows** on a `requests.Session` and **125** on a `curl_cffi` one. Post-fix, all 28 Cockpit metrics and all 44 company cards returned real prices. Then the generated `dashboard.html` was driven in a real headless Chrome **over the DevTools Protocol** — 55 Plotly charts, 0 "Data unavailable", 0 uncaught exceptions across all five pages and all four Economic Data sub-views, plus screenshots of Cockpit/Economic Data/Mining. **This is the first time this project has actually verified the rendered dashboard in a browser** rather than stopping at `node --check` — the standing "not opened in a real browser" caveat attached to nearly every page in this file no longer applies to the core render path.
  - **A methodology trap worth remembering**: the first browser checks used `--headless --dump-dom --virtual-time-budget`, which starves `requestAnimationFrame`. That produced a *false* second bug — the Pulp & Paper / Mining / Agriculture sub-views appeared to build zero charts, and the same file gave 31 charts on one run and 0 on the next. Non-determinism across identical runs is the tell that the harness is lying, not the code. Re-testing over CDP with real time showed every sub-view building correctly. **Don't diagnose lazily-built, rAF-scheduled UI with `--virtual-time-budget`.**
- **Four bank-machine bugs from the first genuinely-working Itaú run — three fixed, one escalated to IT.** Carlo confirmed the yfinance fix worked there, then reported what was still broken. Every one turned out to be a *different* root cause, and none reproduced on the Mac without deliberately simulating the bank's conditions.
  - **All BCB OLINDA charts (16 of 31 on Economic Data) rendered "No data" with no axes.** Not a network block: `agriculture_scraper.py`'s `build_credit()` hit the *same* `api.bcb.gov.br` host successfully in the *same* run. The only material difference was the headers — `fetch_brazil_charts()`/`fetch_credit_charts()` passed `BCB_HDR = {"User-Agent": "Mozilla/5.0", ...}`, a bare truncated UA that is a classic scripted-client signature an inspecting proxy can reject outright, while the working call passes no override and so inherits `DEFAULT_HEADERS`' full Chrome UA. Fixed by making `BCB_HDR` inherit `DEFAULT_HEADERS` (timeout 20→30 to match too). **This is the third instance of the same lesson** (FRED hated the browser UA, MAPA's WAF required it, BCB-via-proxy requires it) — a header set is tuned per-server, never universally safe. Both variants return identical data off-proxy, so the change is verified safe but its *effect* can only be confirmed on Carlo's network.
  - **Pulp & Paper's category pills were frozen on "Pulp" and its 4 KPI boxes were empty.** One cause for both, and not a pill bug at all: `buildPulpPaper()` took an early `return` when FAOSTAT data was missing, and the pill `addEventListener` calls sat *after* that return — so the pills were wired only when the data happened to load. Reproduced exactly by setting `PULP_PAPER_DATA.years = []` in a real browser: pills inert, all KPIs "—". Fixed by wiring the pills unconditionally, before any data-dependent return. **`buildAgriculture()` had the identical latent bug** and was fixed the same way. General rule now: event-listener wiring must never share a code path with data loading.
  - **Agriculture's "Top Producing State" KPI read "No data" for 15 of 16 crops.** The ranking table was queried at `cropsLatest` — the max year across *all* crops — which is 2026, and 2026 exists only for Sugarcane (CONAB's cane bulletin runs ahead of every other series). Soy/corn/rice/wheat top out at 2025, the rest at 2024, so every crop but one was asked for a year it has no data for. Fixed with `_agriCropLatestYear(cropCode)` — each crop ranks on its own newest year, and the displayed year label follows the selection. Verified across all 8 crop pills, with the rankings sanity-checked against real-world knowledge (soy/corn/cotton → Mato Grosso, cane → São Paulo, coffee → Minas Gerais, rice → Rio Grande do Sul, cassava → Pará). **A "global latest" is almost never right for a per-item ranking when the items come from different upstream release cadences.**
  - **FAOSTAT step failed with `403 MediaTypeBlockedDownload` — a corporate control, deliberately not worked around.** Diagnosed precisely by comparing against the ANP zip that *succeeded* in the same run: FAO serves its bulk file as `application/x-zip-compressed` (legacy, non-standard MIME) while ANP serves `application/zip`. So Itaú's proxy filters that exact media type, not ZIPs generally and not that domain. There is no free non-zip alternative (FAOSTAT's `fenixservices` JSON API returns 521; `faostatservices` needs an API key, which §6 rules out). **Routing around an employer's download-scanning control is not this project's call**, so `pulp_paper_scraper.py` now raises a message naming the exact allowlist entry to request instead. The page degrades correctly in the meantime thanks to the pill fix above.
- **News fetching made concurrent, after the per-keyword redesign was reverted for being too slow on the bank network.** Carlo reported the news steps taking an unusable amount of time and erroring on the Itaú machine — with only 10 portfolio companies, against a target of ~150. Two changes, in order:
  1. **Reverted `scraper.py`/`credit_scraper.py` to pre-`d553c86` single-query fetching** (one OR-combined Google News request per company/sector, instead of one per keyword). That redesign had raised those two steps from 17 requests to 89; behind a proxy making each request 5-8x slower, that was the difference between usable and not. **Re-applied the `sys.stderr` UTF-8 fix by hand** — it landed in `957d58b`, *after* `d553c86`, so a plain `git checkout` of the old files would have silently reintroduced the Windows CP1252 crash. Confirmed by diffing `d553c86..HEAD` per file that this was the only thing in the range worth keeping. Verified against real runs: no coverage lost (Portfolio 250→253, Credit 58→68).
  2. **Parallelised the network waits** via a new `core/net_utils.get_many()` — the real fix, because sequential fetching does not scale to 150 companies no matter how few requests each one makes. `ThreadPoolExecutor`, `DEFAULT_WORKERS = 6`, **results returned in input order** so downstream dedup/scoring/merge output is byte-identical to the sequential version. Only the network wait is concurrent: every caller still parses, scores, dedupes and merges sequentially on the main thread, so none of that logic had to become thread-safe. Failures come back in the result tuple rather than raising, matching each scraper's existing continue-past-a-failed-query behaviour.
  - **The sleeps had to go with it, and one had become actively harmful.** `brazil_scraper.py`'s `time.sleep(0.4)` was a politeness delay between sequential requests; once fetching moved up front, that line sat in the *parsing* loop and did nothing but stall 139 iterations over data already in memory — 56s of pure waste, plus 12s of per-sector `sleep(1.5)`. That is why Brazil's first concurrent run only improved 181s→94s instead of the expected ~6x. Removing them took it to 21s. **When you move work off a loop, re-check what the loop's incidental delays are now delaying.**
  - **Measured, not assumed** — before/after on real runs, with article counts compared per company/sector: Portfolio 24s→3.0s, Brazil 181s→20.7s, Credit 18s→1.9s (China untouched at 21s). **Zero articles lost** on any of the three (253/139/68 identical). Rate-limiting was the main risk and was checked explicitly: all 139 of Brazil's term queries returned successfully at 6 concurrent, no 429s, no errors — so 6 is safe against Google News from a single IP. It is deliberately not higher; the deployment target is a shared corporate IP and this project has been burned by rate limits twice (GDELT's lockout, Yahoo's 429).
  - **`update_dashboard.py` now streams each step's output live instead of hiding it.** Carlo reported the run looking stuck on `[1/13] Portfolio news` (it wasn't — just slow). The cause was `subprocess.run(capture_output=True)`: it buffers everything until the child exits and then prints only a 500-char tail *on failure*, so a step that takes minutes showed nothing at all, even though the scraper underneath was printing per-company progress the whole time. Replaced with `run_step()` — `Popen` + a reader thread echoing every line as `│ ...`. **`-u` on the child matters as much as the streaming**: a child Python writing to a pipe rather than a TTY block-buffers stdout, so without it the output still arrives in 4-8KB bursts at the end and live echo buys nothing. Added a `HEARTBEAT_SECONDS` watchdog (prints `… still working (Ns elapsed)` after 20s of silence, so slow is visibly distinct from hung), per-step elapsed time, a total run time, and per-query progress with timings inside `scraper.py`/`brazil_scraper.py`/`credit_scraper.py` (each keyword is its own Google News request, so per-company granularity still left long gaps). The continue-past-failures contract is preserved: a timeout returns `None` and is reported as a failed step rather than propagating. Verified all three paths with synthetic children — heartbeat during silence, stderr captured in the tail on non-zero exit, and kill-at-deadline on timeout.
  - **Per-card Live/Cached freshness marker, closing a real data-honesty gap.** Carlo asked how the Yahoo values were sourced — live or last-known-good — and where they live. Answering it surfaced a genuine gap: `_resilient()` silently substitutes a cached value for any item whose fetch came back empty, and *nothing in the rendered file said so*. The card showed the price and "Yahoo Finance"; only the sparkline's x-axis hinted it had stopped early, and the header's "Updated" timestamp refers to the build, not the datum. On a file that gets emailed to a team, that's a stale number presented as current. Fixed with `_flag_stale()` in `core/generate_dashboard.py`: every item `_resilient()` reused is marked `stale`/`as_of` (its newest real observation date), rendered as a small `● Live` / `● Cached YYYY-MM-DD` badge on the existing source line of Cockpit cards, the three company panels, and Economic Data chart footers. **Both states are labelled, not just the bad one** — "no badge means live" is a convention nobody reading a static file was told about. Marked on a *copy*: the same merged structure is written back to `live_fetch_cache.json`, and a flag baked in there would be wrong next run; verified by assertion that the cache stays clean. Also caught before shipping that the footer's first implementation called `escHtml()`, which is **nested inside the news-clipping code, not global** — it would have thrown at runtime; rewritten to build the footer with `textContent`, so nothing data-derived is ever parsed as HTML and no escaping helper is needed.
  - **MDIC Comex timed out (`ReadTimeout`, 120s) and lost the whole step.** Two problems: the timeout was too short (those yearly CSVs are 50-100MB and a proxy that buffers and scans one before forwarding any bytes trips a read timeout that measures the *gap between bytes*), and `main()` fetched all 6 years in an all-or-nothing loop, so one slow year discarded the five that had already downloaded. Fixed: timeout 120→300, plus per-year fault isolation (`fetch_years()`) that keeps whatever years succeeded and only fails if every one did — same principle as `agriculture_scraper.py`'s `_fetch_section()`.

- A ticker "returning data" isn't the same as it being the *right* data — `JET=F` downloaded cleanly and looked like a normal yfinance response, but a single glance at the actual value (negative) was the tell that something was wrong; pulling the full history confirmed it was a spread/differential contract, not an outright price. When a fetch fails inconsistently or times out for reasons that don't obviously map to network conditions, isolate variables one at a time (headers, timeout, retry count) with direct `requests` calls before accepting "flaky external service" as the diagnosis — that was the right call for GDELT's rate limit (a real, confirmed, documented constraint) but the wrong one here.

- **A government/agency statistical dataset's item hierarchy is not self-evident from item names — verify it against the actual numbers before treating sibling-looking categories as siblings.** FAOSTAT's "Other paper and paperboard" (item 1675) sounds like a residual leftover bucket; it's actually "Total minus Graphic papers," a supercategory that already contains Packaging and Household within it. Treating it as a fourth flat peer category alongside Packaging/Graphic/Household produced a structural-mix chart summing to well over 100%, with "other" as the *largest* slice — an obvious tell once looked at, but only because the actual percentages were checked, not just whether the code ran. Same standard as the `JET=F` negative-price catch: a plausible-looking number from a real, working data source can still be conceptually wrong, and a residual category being the dominant one (or a percentage breakdown not summing to ~100%) is exactly the kind of "does this pass the smell test" check worth running before trusting any newly-integrated classification hierarchy — one level up from checking that a *value* is sane, this is checking that a *category structure* is sane.
- **For a browser-generated downloadable file (News Clipping's `.xlsx`), `node --check`-clean JS syntax is not sufficient verification** — it proves the code parses, not that the *output file* is correct. The higher-value check: actually run the export logic against real/synthetic data with the real library (downloaded the pinned SheetJS bundle rather than trusting the CDN reference blindly), write the file, then *read it back* and assert on its contents — this is what caught nothing in this case (the logic was right first try), but it's the check that would have caught a wrong cell reference, a bad date format, or a hyperlink silently not attaching. Worth the extra few minutes whenever a feature's entire value proposition is "produces a correct file," since a syntax-clean function that writes a subtly-wrong file is a worse failure mode than one that visibly crashes.
- **The "category hierarchy isn't self-evident from names" lesson (FAOSTAT's "Other paper") recurred immediately on the very next external data source (BGS's "Iron and steel" group actually bundling three incompatible physical series)** — this isn't a one-off FAOSTAT quirk, it's a general property of official statistical datasets: broad, human-readable group labels are curated for reporting/publication, not for "safe to sum programmatically." Treat any new dataset's top-level grouping as a hypothesis to verify (pull a sample, check units, check whether sub-items' totals plausibly relate to the group total) before aggregating at that level, every time, not just the first time it bit.
- **Ticker mislabeling is a recurring, not one-off, risk when adding market-data symbols by "obvious" name** — `JET=F` (looked like jet fuel, was a spread contract), `GOLD` (looked like Barrick, was an unrelated company after Barrick's 2025 rename to "B"). Both were caught by checking `yf.Ticker().info`'s actual returned name/metadata against what was intended, not by the fetch succeeding. Company renames and ticker reassignments are exactly the kind of thing that makes a plausible-looking symbol wrong in a way that compiles/runs fine — always confirm the live `shortName` matches the intended company, especially for any ticker recalled from memory/training data rather than looked up fresh.
- **When the user explicitly asks for a concise plan and says "don't repeat what's in CLAUDE.md," honor that literally in the plan's structure, not just its prose density** — the Mining plan skipped re-explaining the by-then-established scraper/render/template pattern entirely and only covered what actually differed (data source, category scope, what's reused vs. newly duplicated). Matching the *scope* of a plan to what's actually new is a distinct skill from writing tersely — a well-trimmed plan for a 3rd instance of an established pattern should visibly shrink relative to the 2nd instance's plan, not just use shorter sentences.
- **`dict.update()` on a nested structure merges only at the top level — a shared outer key gets replaced wholesale, not merged one level down.** Agriculture's `world = _sidra_to_nested(...).get("Brasil", {})` for temporary crops, then `.update()`-ing in permanent crops' `{"Brasil": {...}}` result, silently replaced the whole `"Brasil"` value instead of combining the two crop-code dicts inside it — because both sides had that one shared top-level key. A sanity check (national soy production came back `None`) caught it, not a code review. When merging two dicts that are each `{shared_key: {inner...}}`, extract the inner dicts first and merge those (`{**a[shared_key], **b[shared_key]}`), don't `.update()` the outer structure.
- **A privacy/data-hygiene check belongs in the same "verify the schema before trusting it" pass as a data-quality check, not a separate afterthought.** Before writing any code against MAPA's SISSER rural-insurance CSV, its column list was read first — this surfaced that raw rows carry the insured party's name and a partially-masked document number, columns no other source in this project has ever included. The fix (exclude those columns at `pandas.read_csv(..., usecols=)`, never read them into memory at all, rather than load-then-drop) is cheap when caught before the fetch is written, and is exactly the kind of thing "inspect the actual schema, don't assume" (already this project's standard for category hierarchies and API variables) also protects against.
- **The same default header can help one government domain and break another — always attribute it to the specific server, not treat it as universally safe or universally risky.** `get_with_retry()`'s browser-spoofed default `User-Agent` was added for Google News and previously caused FRED's endpoint to hang (§ Nickel entry above). This session, that exact same default UA was *required* to avoid a 403 from MAPA's `dados.agricultura.gov.br` CKAN WAF — confirmed by testing the identical URL with and without the header, same isolation method as the FRED diagnosis, opposite conclusion. Don't generalize either result across domains; test each new HTTP call site's actual behavior.
- **Government open-data "download" pages are often JS-rendered catalogs whose real file URLs aren't in the page's initial HTML** — MAPA's CKAN dataset page needed a browser `User-Agent` just to resolve which of several dated CSV resource links (`dados_abertos_psr_2006a2015csv.csv`, `..._2016a2024csv.csv`, `..._2025csv.csv`) was current, and CONAB's own download page listed ~20 distinct flat-file names with a stable but non-obvious `/downloads/arquivos/{Name}.txt` pattern that had to be discovered by fetching the actual page rather than guessed from the dataset's display name. Budget one extra research step (WebFetch the real download page, or curl candidate filenames) before assuming a "download" link on a government portal is a plain static URL.
- **When a user insists a limitation "isn't possible," check whether the limitation is even real before re-explaining it — and separately, check whether your own UI is making a real limitation look worse than it is.** Carlo's "2024 is impossible, I need 2026" pushback led to two different, genuine findings: (1) the 2024 ceiling on Pulp & Paper/Mining *was* completely real (re-verified live: BGS's entire 410k-record database's newest entry is 2024; IBGE has zero 2025 PAM rows) — no amount of re-scraping fixes that. But (2) those same two pages had a real, separate bug making the situation look worse than it was: the section text read "World totals, 1961–{{ generated[:4] }}" using the page's *generation* year, not the data's actual latest year — literally claiming 2026 coverage while showing 2024 data. Re-verifying the hard constraint and auditing the UI for self-inflicted misleadingness are two different checks; do both before telling a frustrated user "there's nothing I can do."
- **"Not possible" and "not currently modeled" are different claims — when told the first, actively search for a different source before accepting it, especially a domestic/national one when the blocked source is an international aggregator.** BGS and FAOSTAT genuinely have no 2025 world data — true and unfixable. But Brazil-specific alternatives existed the whole time and simply hadn't been looked for: CONAB's own monthly in-season crop bulletins (as opposed to its finalized annual series) already tracked the 2025/26 harvest, and IBGE's PIM-PF monthly industrial-production index already covered mining and pulp & paper activity through May 2026. Neither replaces the world-level annual statistics — they're narrower (Brazil-only) and different in kind (a current-season estimate, or an index rather than absolute tonnage) — but genuinely extend what's shown, and the plan explicitly labels each as a *complement*, not a *replacement*, so the distinction isn't lost on a viewer.
- **A `groupby()` missing a dimension silently collapses everything sharing the remaining dimensions into one row — and the failure mode is an absence, not a wrong value, which is easier to catch than the next bug below but still easy to miss.** Deduplicating CONAB's monthly crop bulletins to "the latest one per season/state" via `.groupby(["ano_agricola", "uf"]).tail(1)` (missing `"produto"`) picked one row across all 17 co-mingled products per state/season — soy's real, present rows vanished entirely after the groupby while cana/café (one product per file, so structurally immune to this specific bug) looked fine. When deduplicating/aggregating a dataframe that has more than one categorical dimension, list *every* dimension that should stay distinct in the groupby key — leaving one out doesn't error, it just silently merges rows that shouldn't be merged.
- **Two data sources using the same-looking label for different concepts is a real, recurring risk when splicing time series from different agencies — verify the label means the same thing before merging on it, the same discipline as verifying a category hierarchy or a ticker.** IBGE's "year" is a calendar year; CONAB's safra ("2024/25") is labeled by its *start* year — both collapse to the string "2024," but describe non-comparable production cycles. A first version of the crop-splice let CONAB's 2024/25 safra estimate silently overwrite IBGE's already-correct, already-verified calendar-2024 figure under that shared key (a *wrong* value this time, not a missing one — caught only because the pre-splice number had already been independently confirmed, so the post-splice change was noticeably different). The durable fix: when extending a time series from a second source, only ever add years strictly beyond what the first, more authoritative source already has — never let the second source touch a key the first source already populated, even when the labels match.
- **Plain `jinja2.Environment()` does not autoescape by default — only frameworks like Flask that wrap it (`render_template()`) turn that on for you.** This project builds `Environment(loader=FileSystemLoader(...))` directly, so it inherited Jinja's raw default (`autoescape=False`) silently, for the entire life of the project, across every single feature built on it — a gap that had nothing to do with any individual feature and everything to do with the constructor call made once at the very beginning. When auditing *any* Jinja/templating setup that wasn't scaffolded by a framework, check the `Environment(...)` call's actual arguments before assuming escaping is on; "we use a template engine" is not the same claim as "we escape user-influenced content," and this project's news feeds are exactly the kind of external, unmoderated content (RSS titles, GDELT titles) that makes the gap a real one, not theoretical.
- **Turning on autoescape can break the things that were *depending* on raw output on purpose — check for those before flipping the switch, not after.** This codebase pre-serializes ~16 JSON blobs and embeds them directly into `<script>` tags via `{{ x_json }}`; naive `autoescape=True` would have HTML-entity-corrupted every one of them (a `&` inside a company name becoming a wrong, mismatched substring once parsed as JS). The fix wasn't "escape everything" or "escape nothing," it was identifying the one real category of intentionally-raw output and giving it an explicit, narrow safety mechanism (`Markup()` via a small `_safe_json()` helper) rather than either leaving the whole app unescaped or breaking every chart on the dashboard. Also worth knowing directly rather than assuming: Jinja's `{% set x %}...{% endset %}` block-assignment form is *always* captured as pre-safe `Markup`, autoescape setting notwithstanding — confirmed live with a standalone snippet before trusting it, which is what confirmed this project's several `{% set ICON_X %}<svg>...{% endset %}` constants needed zero changes.
- **A verification call to a production write function can silently overwrite the real production artifact if you don't check what the function actually does with its output first.** `render()` in this project doesn't return the rendered HTML string — it writes directly to `OUTPUT_HTML` (`ROOT / "dashboard.html"`, the real file Carlo's team receives). Calling it to inspect synthetic-payload output overwrote the real, ~8MB production file with a small test-data build (confirmed by the size drop, ~8MB → ~278KB) before this was noticed and fully remediated by regenerating from the real pipeline. When verifying a function that writes to a fixed path rather than returning a value, know in advance whether that path is disposable scratch or something real, and prefer capturing output before letting a "just checking" call run against a live target — same category of caution as any other action against shared/production state.
- **When a user gives you a generic, framework-shaped audit checklist (this one visibly written for a React/TypeScript SPA) against a project with a genuinely different architecture, translate the *intent* of each category rather than either force-fitting it or silently dropping it.** "No console errors" and "no broken routes" don't literally apply to a static, server-rendered single file with no client-side router — but the underlying intent (nothing silently fails at runtime, every interactive element actually works) maps cleanly onto this project's real risks: a dangling `getElementById()` reference, an `onclick` pointing at a function that doesn't exist, a filter that produces a blank screen with no explanation. Do this translation explicitly and say so, rather than either padding the audit with inapplicable findings or quietly skipping categories the prompt's author probably did want covered in spirit.
- **When two sources disagree by an implausible, unexplained factor (not close enough to be rounding/methodology noise, not a clean multiple that suggests a known unit conversion), the responsible move is to exclude the data, not to guess at an explanation and ship it anyway.** CONAB and IBGE's coffee production figures differ by ~16x, confirmed via CONAB's own finalized series (not just the noisier in-season one) — too large to be a coffee cherry-to-green-bean ratio (~5-6x) or any other conversion factor found. Rather than pick a plausible-sounding explanation and normalize one side to the other, coffee was left out of the current-season splice entirely, documented as unresolved. A wrong number presented confidently is worse than a gap explicitly labeled as one — this project's standing preference for "honest N/A over quietly wrong," applied to a cross-source reconciliation rather than a single missing metric.
- **A documented, official REST API being unreachable (Cloudflare, a WAF, whatever) doesn't mean the data itself is unreachable — many Brazilian government agencies mirror the same underlying data as plain bulk CSVs on a different, less-protected subdomain, specifically for bulk/programmatic consumption.** `api-comexstat.mdic.gov.br`'s documented API blocked every request from this environment (Cloudflare bot-challenge, no UA trick got past it — a harder wall than MAPA's simple WAF earlier this project). Rather than give up on the source, checked MDIC's own "dados abertos" (open data) page and found `balanca.economia.gov.br/balanca/bd/comexstat-bd/` — a bulk-CSV mirror of the identical data, no protection at all. When a government API is genuinely unreachable, look for the agency's own bulk-download/open-data page before concluding the source is unusable — this is now the second time in this project a bulk-file mirror existed alongside a harder-to-reach "real" API (CONAB's flat files vs. its own web portal is the first).
- **When a chart-grid-building pattern already exists for one page and a second/third data source needs the same treatment, extend the existing spec-builder function rather than building a parallel chart-grid container — this cascades far beyond just less code.** The PIM-PF Brazil-index chart and the later Comex Stat export charts were both added by appending new entries into `_miningBuildSpecs()`/`_pulpBuildSpecs()`/`_agriBuildSpecs()`'s existing return arrays, not by creating new `#miningComexCharts`-style containers. Because those specs then flow through the *same* existing card-building loop, the existing PPTX-export plumbing (`_pptxChartInfo()`'s `'mining'`/`'pulp'`/`'agriculture'` branches, which look up charts by id in `window._miningCharts` etc.) picked up the new charts automatically — a whole planned implementation step ("add a 'comex' branch to `_pptxChartInfo()`") turned out to be unnecessary specifically because the data-plumbing choice one layer down was already correct. Worth checking, before implementing a planned step, whether an earlier design decision already made it redundant.
- **A small formatting/labeling helper used by only 2 callers can hide a real correctness bug that only becomes visible once a 3rd, differently-shaped caller shows up — audit shared formatting helpers the same way category hierarchies get audited, not just once at their original two call sites.** `_rankTableToCSV()` hardcoded `Country`/`(t)`/`World Share (%)` in its CSV header text — invisible as a problem while its only 2 callers (Pulp & Paper/Mining, both country-level, both tonnage) matched those defaults by coincidence. Agriculture's own state-level tables (added earlier this session) already silently mismatched this (CSV said "Country" for a column of Brazilian states) without being caught at the time; it only surfaced when a 3rd table (Mining's new iron-ore-by-state export ranking) made the pattern-mismatch too obvious to miss. Generalized with the same `entityLabel`/`totalLabel` param pattern `_renderRankTable()` already used, and back-filled the fix to the 2 already-wrong Agriculture call sites, not just the new one.
- **A tracked source data file (`portfolio.xlsx`, not a generated cache) can itself have real bugs — a stray duplicate-header row and a stale ticker were both found by actually opening and reading the file, not by assuming a spreadsheet someone else maintains is clean.** The duplicate-header row had already forced a defensive filter into `events_generator.py`'s `main()` at some point in the past — evidence it was a real, previously-hit problem, not a hypothetical one — but nothing had gone back and fixed the row itself, so the same defensive filter would have needed re-adding at every future consumer instead of just once at the source. When a bug's fix is "filter it out in code" rather than "fix the file," that's a signal to check whether fixing the file directly is possible and better — it was here.
- **A quick offline synthetic test, written specifically to exercise the failure modes the requirements describe (not just the happy path), is worth writing even for a small, low-risk addition — it caught a real bug here before a single real page load would have.** `fetch_portfolio_companies()` looked correct by inspection (blank-ticker rows are skipped by an early `continue`), but a synthetic dataframe mixing a real company, a blank-ticker company, a `None`-ticker company, and a stray header-duplicate row showed the last case wasn't actually caught — it would have fetched a nonexistent `"TICKER.SA"` symbol and rendered a confusing "Company: N/A" ghost card, directly violating the one thing the task explicitly required ("do not render empty stock components"). Cost about a minute to write; caught what code review alone hadn't.
- **When a user explicitly says "quality over speed, don't worry about the extra time," that's permission to pick the more conservative technical option even where the cheaper one might have been fine — take it, don't quietly split the difference.** Asked whether to leave `gdelt_scraper.py`'s `BATCH_SIZE` at 5 (unverified but faster) or drop it to 3 (still unverified, but a smaller batch is inherently less likely to overwhelm GDELT's query-complexity handling) — Carlo picked the safer one explicitly, unprompted by any new evidence that 5 was actually broken. That's a legitimate reason to change a value with zero new data behind it; don't wait for a failure to justify a safety margin the user already asked for. (`gdelt_scraper.py` itself was removed entirely shortly after — see below — but the general principle, applied to whatever the next speed/safety tradeoff is, still holds.)
- **A rate-limit lockout from an *earlier, unrelated session* can still be active when a *new* session's very first request goes out — the API gives no way to check its own state before probing it, and probing it *is* the risk.** GDELT's first-ever live validation attempt got an HTTP 429 on request #2 of the run, despite that run itself being perfectly paced (one PT request, a 6s wait, one EN request — no burst). The only explanation consistent with the evidence was a lockout that predated the session. This means "wait until the API isn't rate-limiting me" can't be verified except by trying — which itself risks extending the lockout if done too soon. Practical consequence for any future strict-rate-limit API this project integrates: don't schedule or promise a "next attempt" at a specific short delay; the honest answer is "try again after a real gap, hours not minutes, and accept the first attempt might fail again for reasons outside this session's control." **This specific instance is now moot** — after this exact failure, Carlo asked to eliminate GDELT entirely rather than keep working around its unreliability ("apparently it wont work correctly and it is just one extra thing to break"), and it was removed completely (code, cache, docs) rather than left disabled. Don't re-propose it.
- **Before declaring a scraper redesign successful, compare real before/after counts per company/sector, not just "did it run without errors."** Both `scraper.py`'s and `credit_scraper.py`'s per-keyword-query fixes were verified by reading each cache file's per-key article count before the change, running the real scraper, then reading it again — this is what turned "the code looks right" into "Vale went 30→41, Crédito Bancário went 12→27, nothing regressed." A few keys stayed exactly flat (Itaú Unibanco, Suzano, Gerdau, Custo de Crédito) — recognizing that as a real content ceiling rather than a sign the fix silently failed required already having the "some sectors are just thin, not buggy" pattern established from `brazil_scraper.py`'s own history; a fix that improves *some* rows and leaves genuinely-thin ones flat is success, not a partial failure, and shouldn't be chased further without new evidence something's actually wrong.
- **A CSS `text-transform` only changes what's rendered on screen, not the underlying string — never build a second consumer of that same data (an export, an email, an API response) assuming the visible casing is the real casing.** The News page's importance/company badges render uppercase via CSS, but `core/scoring.py`'s `importance_bucket()` actually returns lowercase (`"high"`/`"medium"`/`"low"`), and company names are stored mixed-case. The Email Clipping feature's color-lookup map was first written with capitalized keys (matching what the badges *look like*), which silently failed to match the real lowercase data — every badge would have rendered in the fallback gray. Caught by checking the actual Python source of truth (`core/scoring.py`) rather than trusting the on-screen appearance, then deliberately re-applying the uppercase transform in the new context (`.toUpperCase()`) instead of depending on a CSS property that might not even be supported there (email clients).
- **When generating a file with real internet-standard structure (an `.eml`, in this case) rather than just an HTML string, the format's own spec-level constraints apply even though nothing before this ever exercised them.** `dashboard.html`'s own HTML content has used non-ASCII typography (em dashes, etc.) freely throughout this project with zero issue, because HTML with a declared UTF-8 charset has no problem with that. An RFC 5322 email header does — raw non-ASCII in a `Subject:` line isn't valid unencoded (needs RFC 2047 encoding to be correct), and could render as mangled text on a stricter or older client. The fix was cheap (a plain hyphen instead of an em dash, only in the header) precisely because it was caught by actually thinking through the target format's real constraints instead of assuming "it's just text" the way every other string in this codebase has been.
- **A "fix Windows encoding crashes" convention that's applied consistently to `sys.stdout` but never checked against `sys.stderr` is only half a fix — and the gap can sit dormant for a project's entire life before a real run finally triggers it.** This project's original CP1252 fix (reconfigure stdout to UTF-8 on every entry-point script) was applied faithfully to all 15 scripts, every time a new one was added — but stderr was never part of that convention, and nothing caught the omission because nothing had printed a non-ASCII character to stderr specifically, on a Windows/Portuguese-locale machine, during a step whose output gets captured-and-decoded by a parent process, until this exact combination finally happened in a real run. When a "fix X everywhere" convention exists, periodically ask "everywhere *what*, specifically" — stdout and stderr are both real output channels and a fix scoped to only one is a gap waiting for the right combination of conditions to surface it, not a completed fix.
- **A subprocess orchestrator's own "continue past step failures" guarantee is only as strong as its weakest failure mode — a crash inside output *capture* is a fundamentally different failure than a non-zero exit code, and a bare `subprocess.run(..., encoding="utf-8")` (no `errors=`) doesn't protect against it.** `update_dashboard.py`'s whole design point is that one step failing doesn't abort the rest — but that logic only runs if `subprocess.run()` actually *returns* a `CompletedProcess` object; if the child's captured output contains a byte that isn't valid UTF-8, the decode happens inside a background reader thread and raises `UnicodeDecodeError` there, which is a real crash, not a clean `result.returncode != 0` case the existing error-handling was ever built to catch. Any orchestrator that captures a child process's text output should default to `errors="replace"` (or an equivalent explicit policy), not just `encoding="utf-8"` — the alternative is trusting that nothing the child (or anything the child transitively imports) ever prints will contain an unexpected byte, which is not a guarantee worth relying on.
